# Звіт про виконання лабораторної роботи №4

Тема: Розробка модульного ядра системи за принципами Clean Architecture та Dependency Injection

Git-тег: `lr4`. Репозиторій: https://github.com/rxcGG/ride-sharing-fleet-management

Хід роботи

## 1. Шари та залежності

Проєкт поділено на чотири шари:

| Шар | Призначення |
|---|---|
| `Domain` | Поїздка, координати, стани та правила їх зміни |
| `Application` | Сценарії створення і завершення поїздки, порти |
| `Infrastructure` | Репозиторій у пам'яті та адаптер сповіщень |
| `WebAPI` | HTTP/gRPC точки входу та реєстрація залежностей |

`Domain` не має посилань на інші проєкти. `Application` залежить від `Domain`. Інфраструктурні класи реалізують інтерфейси, а WebAPI з'єднує їх під час запуску.

## 2. Сценарій завершення поїздки

`CompleteTripHandler` обробляє перехід у стан `COMPLETED` з операції `PATCH /trips/{tripId}/status`. Він отримує через конструктор `ITripRepository` і `ITripNotificationPort`. Сценарій знаходить поїздку, просить доменну модель завершити її, зберігає новий стан і надсилає сповіщення. Якщо поїздка не виконується, домен відхиляє зміну. Сценарій не створює адаптери самостійно.

## 3. Реєстрація залежностей

| Абстракція | Реалізація | Життєвий цикл | Причина |
|---|---|---|---|
| `ITripRepository` | `InMemoryTripRepository` | Singleton | Демонстраційний репозиторій має зберігати дані між запитами |
| `ITripNotificationPort` | `ConsoleTripNotificationPort` | Singleton | Адаптер не зберігає стан окремого запиту |
| `CreateTripHandler` | `CreateTripHandler` | Transient | Обробник не має власного стану |
| `CompleteTripHandler` | `CompleteTripHandler` | Transient | Обробник не має власного стану |

Реєстрації виконані у `src/WebAPI/Program.cs`, який є композиційним коренем.

## 4. Модульні тести

Тести запускаються без бази даних і мережі. Репозиторій та сповіщення замінені простими підробними класами.

| Тест | Що перевіряє |
|---|---|
| `HandleAsync_WhenTripIsInProgress_SavesAndNotifies` | Завершений стан, збереження та сповіщення |
| `HandleAsync_WhenTripIsNotInProgress_RejectsWithoutSaving` | Заборону завершення поїздки в іншому стані |
| `HandleAsync_WhenRepositoryFails_PropagatesPortError` | Передачу помилки порту збереження |

Під час запуску пройшли всі 3 тести.

Лог успішного прогону: `docs/evidence/lr4-tests.txt`.

## Контрольні питання

1. Чому шар Domain не повинен мати посилань на шар Infrastructure?

Тоді правила поїздки не залежать від бази чи фреймворку. Інфраструктуру можна замінити, не змінюючи доменні правила.

2. Чим відрізняються життєві цикли Transient, Scoped та Singleton в DI-контейнерах?

Transient створює новий об’єкт щоразу, коли DI-контейнер видає його для місця використання. Scoped використовує один об’єкт у межах одного HTTP-запиту, а Singleton залишається одним під час роботи програми. Scoped створює один об'єкт на один запит. Singleton створюється один раз і використовується весь час роботи програми.

3. Як використання інтерфейсів репозиторіїв дозволяє тестувати сценарії ізольовано від бази даних?

Сценарій залежить від інтерфейсу, а в тесті замість бази підставляється простий тестовий клас. Тому тест перевіряє логіку без підключення до бази.

Висновок: у роботі створено ядро сервісу поїздок із розділеними шарами та перевірено сценарій завершення. Я закріпив інверсію залежностей і перевірку логіки без бази даних.
